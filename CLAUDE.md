# AutoEngineerBrakeFix - notes for Claude Code

A mod for Railroader's built-in mod loader (Unity/Mono; built against game 0.6.x, played on 0.6.2; entry point `ModEntryPoint` in Main.cs, asset-pack Info.json, settings in Settings.xml). It improves the auto-engineer (AI) on the game's 0.6 rollout controller: smooth throttle, brake-tap and coast-band filters, no power into speed reductions, stall guard, gentle signal braking, speed-limit handling, water stop, shorter steam cutoff, optional realistic fuel use, starting resistance. Namespace `AutoEngineerBrakeFix`, author Exp232. The old PID speed loop was removed in 0.6.0 and its code in this mod in 2.9.1: do not add PID-era patches back.

## Build (cloud sessions: BuildWatcher)
There is no `dotnet`, `mono` or `csc` in the cloud workspace, so the code is never compiled here. The build is done on the user's PC by BuildWatcher (repo `Exp232/BuildWatcher`, `Watch-Builds.ps1`, running as the scheduled task "AutoEngineerBrakeFix Build Watcher"):
1. Make the change in the clone, bump the version (below), commit locally.
2. Zip it: `git archive --format=zip --prefix=AutoEngineerBrakeFix/ -o /mnt/user-data/outputs/AutoEngineerBrakeFix-<ver>-source.zip HEAD`.
3. Save the zip to the user's `C:\Users\exp23\Desktop\Projects\` with `device_commit_files` (`stagedPath` = the zip). The user's standing instruction: always save new builds there. If the bridge is down, say so and give the zip through `SendUserFile`.
4. BuildWatcher (checks every 5 s) sees a zip newer than the repo `Desktop\Projects\AutoEngineerBrakeFix`, and:
   - accepts only `.cs`, `.md`, `Info.json`, the `.csproj` and `.gitignore`, in `AutoEngineerBrakeFix/` or flat (not both), at most 5 MB unpacked; `Info.json` version must equal the file name's; otherwise it rejects it;
   - refuses to build if the `.csproj` changed beyond the version number ("needs review");
   - imports it as a commit `Import v<ver> source`, deleting repo files the zip leaves out (except `.gitignore` and `CLAUDE.md`), builds it, and on success pushes to `origin/main` and deploys to `Documents\Railroader\ModDev\AutoEngineerBrakeFix` (it waits while the game is running or the repo has uncommitted changes);
   - on a compile error it starts a headless Claude that may only edit existing `.cs` files; a fix is pushed as `Fix compile errors in v<ver> (automatic)`; if it can't, `main` stays put, the import goes to branch `incoming/v<ver>` and a GitHub issue lists the errors.
   - Its log is `watcher.log` (build errors included) and `state.json` (zips already handled, by hash) in the BuildWatcher folder. A zip is handled once; to retry the same version delete its entry or bump the version.
5. Never push from the cloud clone: BuildWatcher pushes its own import commits and a push from here would collide. Do not mention unpushed commits to the user (they have said it is not needed). At the start of a session, `git fetch` and reset the clone to `origin/main` before editing, because local commits from an earlier session are not what BuildWatcher imported.
6. A compile error is only known when the user pastes it, or from the Import/Fix commits and the GitHub issue. Be conservative: no local compiler, so grep every renamed member, check brace balance, and keep edits small. The Compiler Explorer tool (`mcp__Compiler_Explorer__compile`, `dotnet100csharpcoreclr`) compiles single files with stub types for the game and Unity; use it to check new logic in isolation, not the whole mod.

On a PC with the game: `dotnet build -c Release /p:DeployToGame=false` (game DLL path from `RailroaderDir` in the csproj, or pass `/p:RailroaderDir=...`). Do not deploy into the game's Mods folder unless asked. A compile-fix job: read the errors, fix them minimally without changing behaviour, repeat until clean, then show the diff.

## Conventions
- Harmony patches (0Harmony.dll ships with the mod). Every patch target and reflected member must be listed in `SelfCheck.cs` under the feature that needs it; private game types are taken as `object __0` and read by reflection (see `StartingResistance.cs`, `SignalPlanning.cs`, `BrakeTaps.cs`).
- The self-check switches a feature off in memory when a target is missing, and saving from the settings window then writes that false into `Settings.xml`. A feature whose patch is only installed when its setting is on must set `AlwaysPatch = true` and the patch must do nothing while the setting is off, so the window can switch it on. If a setting can be saved false by mistake, bump `Settings.CurrentSettingsVersion` and reset it in `Settings.Load`.
- Rollout controller path: `SpeedControlLoop_ApplyRolloutCommand_Patch` (BrakeTaps.cs) rewrites each `RolloutCommand` in this order: `StallGuard.Filter` (returns early when latched), `DirectionStop.Filter` (returns early: train brake only, independent bailed off, while a moving train has no order or target), `ReductionHold.Filter`, `BrakeTaps.Filter`, `CoastBand.Filter`, `RolloutThrottle.Filter` (smoothing), then `CommandLog.Note`. Commands are relative (lever plus or minus 0.125 about once a second) and the controller reads the lever back, so a filter changes its next plan. `ThrottleGlider` eases the lever between ticks and runs `StallGuard.Tick` every frame.
- Target speeds and `MaxSpeedMph` are signed by direction of travel: compare magnitudes. `gradeUnderPct` negative = uphill in the direction of travel.
- Waypoint and Yard modes must keep the game's stopping accuracy; reduced accuracy only in Road mode.
- Keep defaults stable; the code defaults in `Settings.cs` are the user's own settings. When changing behaviour or a setting, bump the version in `Info.json`, `BUILDING.md` and the csproj together (all three; a version must be higher than the last import for BuildWatcher to take it) and add a `CHANGELOG.md` entry (newest first, under `# Changelog`). Update `README.md` for user-visible features. Removing a settings field is safe: XmlSerializer ignores unknown elements.
- Structs: `AutoEngineerPersistence` and `Orders` are structs, so assign a property through a local (`var p = new AutoEngineerPersistence(...); p.Orders = ...;`), never on a temporary (CS1612). The game calls the independent brake the locomotive brake (`LocomotiveBrake`); use that name in the settings window.
- Game physics notes: the game uses the Davis equation for resistance, journal bearings for everything, slack of about 0.04 m per coupler, per-car static friction via `IntegrationSet.ApplyBrakes`. `StartingResistance` adds a standing-start drag with an oil-film standing-time factor on top.
- In-game settings window: `SettingsUi.cs` (the game's `UIPanelBuilder` through `WindowManager.Shared.RegisterCustomWindow`, hotkey Ctrl+F8). `BuildPage` draws the page without a scroll view so the Mod Settings Hub can host it; `HubLink.cs` registers the page with the hub by reflection (copy of the hub's `HubLink.Template.cs`; do not list the hub in Info.json). A new setting that is read while the game runs should get a slider or toggle there, and `ResetDefaults` must reset it.

## Workflow
Logs (`ae_*.csv`, `signals_*.csv`, `fuel_summary_*.csv`) and decompiled game code come from the user. Log time = the file's start clock minus the first `t`; a new log opens each time the engineer is enabled. Useful columns: `cmdKind`, `cmdThr`, `outThr`, `cmdMod` (tap, which also marks the no-power-into-reductions hold; band; smooth), `cmdAgeS`, `nextTargetMph`, `nextTargetDistM`, `ctxTargetMph`, `gradeUnderPct`, `gravityKN`. This repo is the source of truth: if you fix something here, tell the user so they can pass the diff back. Project notes live in the Railroader Modding project's `claude/` docs.
